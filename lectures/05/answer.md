### 基礎

- 取り組んだレベル：基礎
- やったこと：`app/config.py` の `RAG_TOP_K` を `5` から `3` に変更し、通常のベクトル検索で返す最大件数を減らした。
- 比較した質問と、固定した条件：質問は「第2回の説明では、LoRAは何を固定し何を学習しますか？ QLoRAは何を加えますか？」。モデルは既定の `gemini-3.5-flash-lite`、検索対象は第1〜3回の本講義資料。変更前後で同じ質問と条件を使う予定。
- 結果：変更前の `uv run python -m app.agent --trace '第2回の説明では、LoRAは何を固定し何を学習しますか？ QLoRAは何を加えますか？'` は、`GEMINI_API_KEY` が未設定のため終了した。`[model] gemini-3.5-flash-lite` の表示後に認証情報の案内が出ており、ツール呼び出し・回答・根拠・所要時間・トークン数・費用は取得できなかった。変更後も同じ理由で未実行のため、前後のトレース比較は未完了。
- 改善した例と、残る失敗・制約：検索結果数の上限は5件から3件になったが、今回の質問で必要な根拠が残るか、回答がどう変わるかは未確認。上位3件から漏れた根拠が必要な質問では回答品質が下がる可能性がある。
- 気づき・疑問：検索件数を減らすと、不要な候補が減る一方で必要な根拠を取りこぼす可能性もある。APIキーを環境に設定したうえで、変更前の値 `5` と変更後の値 `3` で同じ質問を `--trace` 付きで実行し、ツール引数・回答・引用根拠を比較する必要がある。

### 実装

- 取り組んだレベル：実装
- やったこと：`app/retrieval.py` で通常の検索ヒットに同じ資料内の前後ページを追加し、重複ページは1件にまとめるようにした。追加ページには、どの検索ヒットに関連しているかを示す `context_for` を付けた。Graph検索は従来どおりベクトル検索のヒットだけを入口にする。`RAG_TOP_K=3` は基礎編から変更していない。
- 比較した質問と、固定した条件：質問は「第2回の説明では、LoRAは何を固定し何を学習しますか？ QLoRAは何を加えますか？」。モデルは既定の `gemini-3.5-flash-lite`、検索対象は第1〜3回の本講義資料。質問・モデル・資料・検索件数を変えず、取得処理だけを比較する想定。
- 結果：実モデルでの変更前後の回答・根拠・時間・トークン数・費用は、`GEMINI_API_KEY` が未設定のため未取得。代わりにAPIを使わないテストで、検索ヒットp2・p4に対して同じ資料のp1・p3・p5を追加し、p3は重複せず両方のヒットとの関連を保持すること、別資料のページを混ぜないことを確認した。
- 改善した例と、残る失敗・制約：前後ページに必要な説明が続く場合、検索上位に入らなかった本文もエージェントに渡せる。一方、隣接ページが無関係な場合にも追加され、入力が増える。今回の質問で実際に有効な根拠が増えるかは未確認。
- 気づき・疑問：隣接ページは検索スコアで順位付けしたヒットではないため、`context_for` で出所を明示した。APIキーを設定して同じ質問を再実行し、追加ページが回答の根拠として使われるかを確認したい。

### 発展

- 取り組んだレベル：発展
- やったこと：`app/retrieval.py` の Graph 検索を改良した。質問に含まれるGraph上の用語ノードを特定し、その用語に `mentions` で結ばれたページとの一致数が多い候補を優先する。候補には一致した用語を `query_matched_terms` として付ける。`app/agent.py` の指示では、一致語だけで根拠とせず本文で確認するようにした。
- データ構造と選んだ理由：既存Graphの `page`・`term` ノードと `mentions`・`next_page` エッジを再利用する。実行時に質問語と一致したterm IDの集合、ページごとの一致term集合を作り、一致数の降順、hop数、既存の優先度で候補を並べる。新しい索引やGraphファイルを作らずに、複数概念を含む質問で質問に関係するページを上位に出すため。
- 比較した質問と固定した条件：質問は「第2回のチャットボット例で、構造化出力・資料固有の知識に、LoRA/QLoRAとRAGをどう使い分ける？」。基本RAGとGraphで同じ質問、既定モデル `gemini-3.5-flash-lite`、第1〜3回の本講義資料を使う。`RAG_TOP_K=3` とGraphのhop・件数設定は固定。
- 結果：基本RAG・Graphとも `--trace` 実行を試したが、`GEMINI_API_KEY` 未設定で終了し、回答・実際の検索結果・時間・トークン数・費用は取得できなかった。APIなしのGraph確認では、p.52を固定seedとして同じ質問を展開すると、p.53「チャットボットの場合：何をFTし、何をFTしないか」（一致語：RAG・構造化出力）とp.51「PEFT：モデル全体ではなく、一部だけを学習する」（一致語：LoRA・QLoRA）が候補に含まれた。この確認はベクトル検索を通した実行ではない。根拠資料ではp.52がLoRA/QLoRA、p.53が出力形式と資料固有の知識を扱っている。
- 改善した例と、残る失敗・制約：複数の話題が混在する質問で、質問語に対応するページが候補に含まれることをオフライン確認した。一方、APIを使った基本RAGとの回答・根拠比較は未完了。Graphの用語ラベルにない言い換えは一致しない可能性があり、一致語が多くても本文が答えの根拠になるとは限らない。
- 気づき・疑問：語の一致を候補順位付けに使うだけで、回答根拠の正しさは保証しない。APIキーを設定して同じ質問を基本RAGとGraphの両方で実行し、p.53などの根拠が回答に使われるか、余分な候補が増えないかを確認したい。
